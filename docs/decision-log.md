## D031｜Phase 2 第四批第一阶段：先收紧数据安全，再处理可用性优化（2026-08-09）

- **决策：** 已实施并验收：邮件自动关联改为复用申请状态机，仅允许高置信、公司与岗位精确且唯一、当前阶段可合法推进的申请；同一 `EmailEvent` / 幂等键只会产生一次关联事件。已结束、冲突、非唯一或重复请求保留为待确认。
- **删除策略：** 只要岗位存在任一 `Application`，一律拒绝删除；不级联删除，也不在本批新增删除申请或“结束后删除岗位”的路径。
- **数据可恢复性：** 新增不含密钥、授权码、邮箱地址、邮件全文、附件或截图原图的 JSON 全量导出；恢复先在隔离 SQLite 库验证，再备份并全量替换当前库，不支持合并。替换/健康检查失败时从替换前备份回滚。
- **迁移：** `JobStore.initialize()` 改为执行 Alembic `upgrade head` 并验证 schema；历史运行期 schema 初始化仅保留为迁移测试参考，不再用于应用启动。
- **验证：** 新增高置信邮件对已结束申请、重复同一邮件、关联岗位删除、导出/隔离恢复/坏文件回滚、旧库 Alembic 升级的自动化测试。
- **未纳入：** 雷达筛选入口、长标题布局、邮件同步诊断性、AI 匹配与邮件解析升级仍按决策卡后续阶段处理。
## D032｜Phase 2 第四批第一阶段验收修订：确认、脱敏与重启检查（2026-08-09）

- **删除：** 无关联申请岗位也必须有服务端确认参数；任何拒绝反馈显示关联申请数量。存在任一申请时始终拒绝，未新增删除申请路径。
- **导出：** 改用字段白名单和邮箱统一脱敏，排除 `message_id`，并记录 `app_version`。
- **恢复：** Web 仅执行隔离验证、备份、全量替换并写入等待重启标记；它不报告恢复成功。下一次启动通过 Alembic/schema/外键检查后才确认成功。
- **迁移：** 非 head 本地库在 Alembic 升级前自动备份；不可逆数据安全迁移要求通过备份恢复。
## D033｜Phase 2 第四批第一阶段前台入口补齐（2026-08-09）

- **数据管理入口：** 将“数据管理”加入所有服务端渲染页面导航，确保导出/恢复不是隐藏 URL 功能。

## D035｜Phase 3B 冻结前相对时间安全修正（2026-08-20）

- **决策：** 用户确认只修复邮件相对时间的错误绝对化。当前邮件理解 payload 不传递具时区语义的 `received_at`，因此“收到邮件后 48 小时”“明晚”“本周五前”等没有明确日历日期的表述，不得计算或保存为 ISO 时间。
- **处理：** 以模型提示和引用证据后处理双重约束清空推断的安排/Deadline，保留摘要与证据，沿用既有提醒和人工确认边界。邮件含明确日历日期时继续保留正常结构化结果。
- **非目标：** 不变更候选召回、页面、schema、数据库、状态机或邮件接收时间架构；未来是否以真实 `received_at` 计算相对时间需另行确认时区和数据契约。
- **验收：** 2026-08-20 针对性测试 35 passed、全量回归 101 passed；12 封现有邮件基准本地门禁 12/12，实时模型 11/11 成功且时间/证据引用 11/11；8 封真实风格时间样本 8/8 通过。
- **状态：** 已验收。
