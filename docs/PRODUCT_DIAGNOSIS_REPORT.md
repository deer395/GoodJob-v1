# 秋招管理系统产品诊断报告

> 诊断日期：2026-08-09
> 诊断范围：`manual_capture/` 当前实现、Alembic 迁移、项目/决策文档、自动化测试，以及用户提供的 10 张运行截图。
> 本次仅审查并新增本报告；未修改应用代码、配置、现有 SQLite 数据或用户已有文档。

## 1. 当前产品状态评价

### 完成度

当前 GoodJobAI 已不是只能录入岗位的原型。实际已形成下列本地单机流程：

```text
手动录入 / CSV、XLSX 导入 → 秋招雷达与画像规则匹配
→ 准备投递与检查单 → 用户手动确认已投递
→ 申请事件、进度列表/表格/月历、ICS 导出
→ 可选的 JD AI 辅助与本地 IMAP 邮件待确认
```

岗位、申请和申请事件已分离建模；手动投递权、AI 显式同意、邮件正文最小化留存等关键边界也在实现中得到体现。就“一个人持续管理秋招”这一核心任务而言，产品已经达到**可进行真实试用的个人工具**水平。

但它尚未达到可长期放心使用的成熟软件产品标准。最大差距不在功能数量，而在三个方面：

1. 关键数据的完整性与可恢复性尚不够稳固；
2. 多个已实现能力没有形成清晰、低摩擦的用户闭环；
3. AI 匹配与邮件解析的结果虽然受控，却仍偏“单次、轻规则/轻提示”，缺少可校验的决策框架与持续纠错机制。

### 优点

- 产品边界清楚：没有自动投递；投递完成由用户确认；低置信邮件默认进入待确认。
- 主数据模型方向正确：`JobPosting → Application → ApplicationEvent` 使投递前和投递后信息不混淆。
- 基础异常反馈可用：必填项、日期、候选重复、AI 未配置/失败、导入会话过期等都有明确反馈或安全降级。
- 导入采用预览、映射、去重和确认三步，ICS 只导出符合规则的事项，设计克制。
- 视觉语言基本统一：蓝白色、卡片、标签、状态色一致；截图中的表格/日历信息表达已具备产品感。
- 自动化验证具有基础广度：本次实际运行 `D:\ANACONDA\python.exe -m pytest manual_capture/tests -q --basetemp .pytest_tmp\product_diagnosis_full`，结果为 **48 passed, 1 warning**。覆盖了收录、重复、匹配、申请流转、导入、ICS、AI 降级和邮件确认等主要路径。

### 产品成熟度判断

当前更像 **B. 高完成度的个人/内部工具**，正向商业产品过渡。

原因是：信息结构、持久化和核心流程已经超过开发演示；但首次引导、发现性、数据备份/恢复、异常可观测性、关键数据保护、全流程编辑与产品化文档仍不足。它适合熟悉系统的单个用户使用，不宜在现状下承诺“长期无忧管理所有秋招记录”。

## 2. 问题列表

严重程度口径：P0 为可能错误改变/损坏核心申请数据；P1 为明显影响长期使用、数据安全或核心任务成功；P2 为明显体验和维护性问题；P3 为可选优化。

### P0-01：邮件自动关联可绕过申请状态流转，可能把已结束申请重新推进

- **问题：** 高置信邮件会通过 `should_auto_apply_email()` 选中所有“非待投递”申请；`resolve_email_event()` 随后直接更新申请状态，没有检查当前申请是否已结束、是否允许该阶段跃迁，也没有防止同一邮件类别重复写入。收到晚到或误判的高置信邮件时，已结束申请可能被改回测评、面试或 Offer。
- **位置：** `manual_capture/app.py`：`exact_email_matches`、`should_auto_apply_email`、`resolve_email_event`、`/api/email-events`。
- **影响：** 会静默污染最关键的申请阶段，直接违背“低风险自动化不得污染流程状态”的产品原则；用户可能遗漏真正需要处理的申请。
- **严重程度：P0 - 必须修复。** 自动关联应只允许处于明确可推进状态的唯一申请，并复用与手动推进相同的状态机校验；已结束、冲突和重复事件必须转人工确认。

### P1-01：删除岗位会留下孤立申请和事件，且没有删除确认/恢复机制

- **问题：** `delete_job()` 只删除 `job_postings`。SQLite 连接未开启外键约束，`applications`、`application_events` 和检查单不会同步处理；进度查询依赖与岗位表的内连接，孤立申请会从页面消失。接口也没有撤销期、确认页或恢复方式。
- **位置：** `manual_capture/app.py`：表定义、`connection()`、`delete()`、`POST /jobs/{job_id}/delete`。
- **影响：** 一次删除可造成申请历史在 UI 中不可见，破坏长期记录完整性。
- **严重程度：P1 - 强烈建议修复。** 在产品开放删除入口前，应明确采用“禁止删除存在申请的岗位”“软删除”或“经确认级联删除并可恢复”之一，并以外键/事务保证一致性。

### P1-02：没有全量数据导出与恢复路径，无法满足长期个人数据可恢复要求

- **问题：** 当前只存在 `/calendar/export` 的 ICS 导出；没有岗位、画像、申请、事件、导入批次和邮件结构化数据的 JSON 全量导出，也没有导入/恢复说明。
- **位置：** `manual_capture/calendar_routes.py`、路由与模板；仓库内未发现数据导出接口或测试。
- **影响：** 本地 SQLite 损坏、迁移失败、换机或误操作后，用户不能以产品内能力恢复完整求职记录。
- **严重程度：P1 - 强烈建议修复。** 优先提供不包含 API Key、授权码、邮件全文和敏感原文的 JSON 导出，以及经过验证的恢复说明。

### P1-03：雷达已实现的“视图/筛选”能力大部分没有可发现入口

- **问题：** 后端支持 `today`、`week`、`favorite`、`high`、`near`、`expired` 等 `state` 筛选，但雷达页面只呈现搜索框、排序下拉和统计卡。用户无法从界面直接进入“今日新增”“本周截止”“收藏”“高匹配”等核心工作视图。
- **位置：** `manual_capture/app.py`：`JobStore.list()`、`GET /jobs`；`manual_capture/templates/pool.html`。
- **影响：** 已开发的优先级能力不可发现，用户仍需在长列表中找岗位，削弱“雷达”的产品价值。
- **严重程度：P1 - 强烈建议修复。** 将核心视图做成可见筛选标签，并展示当前筛选条件、结果数及可清除入口。

### P1-04：长职位标题挤压主操作，列表无法稳定支持真实校招数据

- **问题：** 雷达和投递工作台的岗位标题直接在单行卡片头部展示，未提供稳定截断、摘要或详情页。用户截图中“华安证券”等超长职位已经把“查看详情/投递完成”压缩为窄列逐字按钮。
- **位置：** `manual_capture/templates/pool.html`、`applications.html`；`manual_capture/static/app.css` 的 `.job`、`.job h2`、`.job-actions`。
- **影响：** 主操作可读性和点击效率下降；这类合并职位/业务线文本在秋招数据中很常见。
- **严重程度：P1 - 强烈建议修复。** 卡片应限制标题行数、保留完整标题于详情，操作区保持最小宽度；最好要求导入时拆分多岗位，而不是把多职位串成一条可投递记录。

### P1-05：邮件同步的运行状态与失败原因对用户不可诊断

- **问题：** IMAP Agent 只取近 7 天、最多 50 封候选主题；页面只有“同步邮箱”按钮和通用结果消息。没有可见的邮箱配置状态、上次同步时间、扫描范围、候选数/去重数、网络/鉴权/本地服务失败的区分，也没有“未配置”前置引导。
- **位置：** `manual_capture/imap_agent.py`；`manual_capture/app.py`：`/api/email-sync`；`manual_capture/templates/progress.html` 邮件视图。
- **影响：** 用户面对“没有结果”时无法判断是确实无邮件、主题过滤过严、授权失效、网络失败还是端口/Agent 问题，难以长期信任邮件流程。
- **严重程度：P1 - 强烈建议修复。** 在不保存正文和凭据的前提下，展示本地配置检查、上次同步、扫描范围、结果摘要与可操作错误；真实 IMAP 联通/权限失败尚未在本次诊断中执行，需补充集成验收。

### P1-06：AI 匹配是两套并列分数，缺少统一决策口径和校验反馈

- **问题：** 规则分由城市、方向、技能、学历做加分，方向/技能只取第一个命中标签；AI 另返回一个 0–100 分。页面同时显示“规则匹配”和“AI 辅助判断”，没有说明二者如何共同影响优先级、哪一项是硬门槛、何时应人工复核，也没有用户标记“准确/不准确”的反馈闭环。
- **位置：** `manual_capture/matching.py`、`manual_capture/ai.py`、`manual_capture/templates/pool.html`。
- **影响：** 分数容易被理解为精确结论，实际却未覆盖目标行业、约束、JD 必要条件、经验要求、权重校准与反例；无法持续提升准确度。
- **严重程度：P1 - 强烈建议修复。** 该问题与你提出的第一点一致。下一轮应先做“硬规则 → 结构化证据 → 可解释排序 → AI 仅补充语义缺口”的统一模型，并记录用户纠错；本报告不建议现在直接更换算法或参考外部项目后照搬。

### P2-01：第一次打开虽不空白，但缺少“从零开始”的任务引导

- **问题：** 首页直接提供完整录入表单，三个必填字段与“查看岗位池”清晰；但没有说明新用户应先收录、何时配置画像、如何进入投递及进度管理，也没有首条记录示例或新手路径。
- **位置：** `manual_capture/templates/capture.html`；用户截图 1、2。
- **影响：** 用户知道可以填表，却不一定理解产品全旅程；AI 区块还可能在第一屏抢占核心录入注意力。
- **严重程度：P2 - 产品体验优化。** 首次使用时增加简短的三步任务说明，并把画像配置放在“已有若干岗位后”的可选提示中。

### P2-02：导航是平铺页面名，缺少按用户任务组织和当前待办入口

- **问题：** 顶部并列“手动收录岗位、秋招雷达、投递工作台、申请进度、求职画像、AI 设置”。它没有区分主流程和设置，也没有把“今天该做什么/临近 DDL/待确认邮件”作为全局入口或角标。
- **位置：** 全部主要模板的重复 `<nav>`；用户截图 1、3–10。
- **影响：** 新用户难以形成从岗位到申请的心智模型，频繁任务切换时也缺乏行动优先级。
- **严重程度：P2 - 产品体验优化。** 按“岗位”“投递”“进度”组织主导航，将画像和 AI 归为设置；在主导航或首页提供待投递、临期、邮件待确认的行动计数。

### P2-03：岗位详情依赖 modal，缺少可分享/可刷新/可回退的稳定详情页

- **问题：** 雷达点击“查看详情”打开 `<dialog>`；URL 不变，浏览器回退和刷新不能代表详情状态，长信息与多个操作会集中在弹窗内。
- **位置：** `manual_capture/templates/pool.html`。
- **影响：** 对需要反复核对 JD、编辑、准备投递和 AI 证据的真实岗位，空间与导航能力不足，也不利于从进度页回到同一岗位。
- **严重程度：P2 - 产品体验优化。** 详情应成为独立页面或至少具有可复制的稳定 URL；modal 更适合短预览。

### P2-04：申请进度信息密度高，但“下一步”并未始终成为首要动作

- **问题：** 列表页同时展示漏斗、筛选、卡片、事件、阶段操作；表格页展示更强，但行动截止/安排含义需靠文字理解。截图中“下一步：尚未设置”并未形成明确的补全行动。
- **位置：** `manual_capture/templates/progress.html`、`_progress_table.html`、`calendar.html`；用户截图 5–7。
- **影响：** 用户能看到数据，却不一定能在数秒内回答“我今天要做什么”。
- **严重程度：P2 - 产品体验优化。** 增加按时间排序的“待我处理”区域；对无下一步、临期、逾期使用明确的主按钮和文案。

### P2-05：没有独立公司实体；“管理公司信息”目前无法完成

- **问题：** 公司只作为岗位上的自由文本字段保存，未实现公司档案、别名合并、公司维度的岗位/申请聚合或公司备注。
- **位置：** `job_postings.company` 及相关模板；未发现 Company 模型或页面。
- **影响：** 用户提出的“管理公司信息”在当前产品中没有入口，只能逐条岗位编辑。
- **严重程度：P2 - 产品体验优化。** 这不是既有功能失效，而是当前未实现的能力；是否引入 Company 实体应先做决策卡，避免超出当前模型范围。

### P2-06：导入预览只展示前 10 行，后续异常在确认时才暴露

- **问题：** 导入会对全量行计算校验，但界面仅展示前 10 行；第 11 行之后的无效字段或日期问题在执行时才提示并回到预览。
- **位置：** `manual_capture/import_routes.py`：`preview_import()`、`execute_import()`；`templates/import.html`。
- **影响：** 大批导入时用户难以在确认前了解所有风险，需要来回修正。
- **严重程度：P2 - 产品体验优化。** 预览页至少应汇总所有问题行、提供分页/下载问题清单，并明确显示“将创建/更新/跳过”的全量计数。

### P2-07：缺少统一、面向用户的错误页和恢复动作

- **问题：** 不存在的岗位、导入批次或应用会抛出 FastAPI `HTTPException`，通常返回技术性 JSON/默认错误，而非站内错误页；部分路由有友好重定向，部分没有。
- **位置：** `manual_capture/app.py`、`manual_capture/import_routes.py`、`calendar_routes.py`。
- **影响：** 刷新过期链接、手工输入错误 URL 或数据被删后，用户可能看到无法理解的页面。
- **严重程度：P2 - 产品体验优化。** 增加 404/400/500 的统一模板、返回入口和不丢失输入的恢复说明。

### P2-08：数据模式与 Alembic 双轨维护，迁移可信度不足

- **问题：** `JobStore.initialize()` 在应用启动时执行大量 `CREATE TABLE` 和 `ALTER TABLE`，同时仓库又维护 Alembic 迁移。当前数据库可能因“启动应用”而变更，而不是由已记录、可回滚的迁移变更。
- **位置：** `manual_capture/app.py`：`JobStore.initialize()`；`alembic/versions/`。
- **影响：** 测试、开发机和用户旧库容易出现 schema 漂移；恢复、升级和排障成本升高。
- **严重程度：P2 - 工程质量优化。** 将 schema 演进收敛至 Alembic，启动时只检查版本/给出升级指引；保留的兼容逻辑需有明确退役计划和迁移测试。

### P2-09：单一超大模块与重复模板降低迭代安全性

- **问题：** `manual_capture/app.py` 同时承担 schema、数据访问、领域规则、外部调用编排与全部路由，文件约 84 KB；六个页面各自复制顶栏 HTML。
- **位置：** `manual_capture/app.py` 与 `manual_capture/templates/*.html`。
- **影响：** 小改动易误伤无关流程；导航文案/可访问性/缓存修复需要重复修改。
- **严重程度：P2 - 工程质量优化。** 按 store、服务、路由拆分，并提取基础布局模板；这是渐进式重构，不应与 P0/P1 修复捆绑成大改。

### P2-10：仓库中遗留大量测试数据库与结果目录，工作区卫生较差

- **问题：** 工作区存在多组 `pytest_*` 目录、SQLite 文件和未跟踪诊断/修复材料；其中还出现无法枚举的目录。它们不属于产品运行资产，也使 `git status` 噪声很大。
- **位置：** 仓库根目录。
- **影响：** 容易误提交测试数据，掩盖真正改动，并增加备份/检索成本。
- **严重程度：P2 - 工程质量优化。** 先确认保留清单，再将测试产物统一放入可忽略的临时目录并清理历史残留；本次诊断未删除任何文件。

## 3. UI/UX 优化建议

| 页面 | 当前问题 | 优化方案 | 预期效果 |
|---|---|---|---|
| 首次首页 / 手动收录 | 可直接填写但没有产品旅程和首要任务说明；AI 区块可能先于人工录入抢占注意力。 | 空状态提供“收录第一条岗位 → 配置画像 → 准备投递”的三步引导；AI 作为折叠的可选加速器。 | 新用户在首次访问即可理解下一步，不把 AI 当成使用前提。 |
| 秋招雷达 | 统计卡不可点击，后端筛选不可发现；超长标题挤压操作。 | 增加“全部、今日新增、本周截止、收藏、高匹配、临期”筛选标签；卡片标题两行截断，固定右侧操作区。 | 从“浏览列表”变成“找到今天应处理的岗位”。 |
| 岗位详情 | 弹窗承载完整信息、编辑、AI 分析和准备投递，URL 不稳定。 | 使用独立详情页；保留弹窗仅做简要预览。详情页分为岗位信息、匹配依据、投递准备三段。 | 支持回退、刷新、深度核对和连续操作。 |
| 投递工作台 | 待投递和已投递分栏清楚，但检查单和材料版本不在主页面可见；长标题影响按钮。 | 在待投递卡上显示检查完成度、DDL、缺失投递链接；把“投递完成”放在稳定主操作位置。 | 降低从“值得投”到“已投递”的遗漏率。 |
| 申请进度 | 漏斗、卡片、表格、日历分别有价值，但没有集中回答“今天做什么”。 | 在顶部增加“待我处理”队列：逾期/今日/未来 3 天、未设下一步、邮件待确认；列表/表格/日历继续作为查看方式。 | 用户能快速做出下一步行动，而不是只浏览历史。 |
| 邮件待确认 | 隐私提示很清楚，但同步健康度与无结果原因不清晰。 | 显示本地配置状态、上次同步、扫描范围、候选/去重/失败数；失败给出恢复步骤，保留“手动补记”主路径。 | 提高对邮件自动化的可理解性和信任。 |
| 求职画像 / AI 设置 | 画像字段足够，但与雷达结果的关系弱；AI 设置只展示同意记录。 | 画像保存后展示“将影响哪些规则”；AI 分析结果统一显示输入范围、证据、有效期和“有帮助/不准确”反馈。 | 降低黑箱感，为后续匹配优化积累真实反馈。 |

## 4. 功能流程优化建议

### 建议的核心任务流

```text
岗位入口
  收录 / 导入
      ↓
雷达：按“今天需要判断”排序，显示匹配依据与 DDL
      ↓
岗位详情：确认资格、材料、官方链接
      ↓
投递工作台：完成检查单 → 用户在官方渠道提交 → 手动确认
      ↓
申请进度：待我处理 → 事件/下一步 → 邮件人工确认 → 日历/ICS
```

### 具体建议

1. 在雷达把筛选变成任务视图，而不只是搜索结果；统计数字可点击进入对应列表。
2. 对导入的“一个公司 + 多个职位串”增加拆分提示或导入前质量告警，避免进入后续流程后才发现一条记录不可操作。
3. “准备投递”后应在工作台明确展示检查单、简历版本和缺少官方链接/DDL，不让用户必须来回打开详情。
4. 投递确认后要求或强提示填写“下一步行动”；如果暂时未知，也明确记录“等待何种通知、何时回看”。
5. 邮件确认始终先展示“匹配到哪个申请、为什么匹配、将写入什么事件、哪些时间待确认”；自动关联只作为满足严格状态机规则后的例外。
6. “公司管理”目前不应假装存在。若真实使用中常需看同一公司的多岗位和多申请，再单独决策是否增加 Company 及别名模型。

### AI 匹配与邮件解析：本轮是否应同步修改

应当**记录为下一轮的重点改进，但不建议在当前诊断后立即直接改代码**。原因是两者都涉及数据口径、自动化权限和验收集，而不是单纯“调高分数/换一个 prompt”。

- **AI 匹配：** 先建立可解释的统一评分卡：硬淘汰（届别、学历、城市、明确限制）→ 必要条件证据 → 偏好匹配与 DDL/来源等排序因素 → AI 只评估规则难覆盖的 JD 语义。每一项都应显示命中的原文证据、置信度、未覆盖项，并允许用户标记正确或错误。之后再有针对性地研究/对比开源实现和市场方法；本次没有进行外部竞品或开源项目调研，因此不对其效果作推断。
- **邮件解析：** 先把“同步健康、候选筛选、分类、公司/岗位关联、时间解析、用户确认”拆为可观测步骤。解析结果须保留来源片段和不确定性；模糊关联、已结束申请、重复/冲突事件一律进入确认队列；每次人工修正应成为回归样本。真实 IMAP 服务、账号权限和模型服务尚未在本次诊断中调用，因此联通可靠性结论为“待验证”。

## 5. 工程质量建议

1. **先建立数据完整性护栏。** 所有会改变申请阶段的入口（手动推进、邮件确认、自动关联）必须经过同一状态机和幂等检查；为岗位—申请—事件明确外键策略与删除策略。
2. **实现并验证备份恢复。** 提供安全 JSON 导出；用隔离数据库做“导出 → 新库恢复 → 数量/关联一致性核验”的自动化测试。
3. **统一数据库迁移。** 以 Alembic 为 schema 的唯一演进来源，补充从旧库升级到最新版、降级或备份恢复的测试。
4. **补齐关键端到端测试。** 现有 TestClient 覆盖良好，但仍建议增加：已结束申请收到高置信邮件、删除有申请的岗位、无效/过期链接的站内错误页、完整导出恢复、长标题断点和移动端主操作。
5. **保留现有隐私优点。** 不记录 API Key、IMAP 授权码或邮件全文；对外部 AI 调用继续保持字段白名单、显式同意和失败后可手动完成任务。
6. **收敛模块边界。** 在 P0/P1 修复稳定后，再逐步拆分 `app.py`，提取页面基模板；不要为重构改变已确认业务状态定义。
7. **治理测试产物。** 明确哪些数据库/备份应保留，其他 pytest 目录进入统一临时位置并在 `.gitignore` 中覆盖，清理前必须征得确认。

## 6. 修改优先级路线

### 第一阶段：数据可信与长期可恢复（P0/P1）

- 收紧邮件自动关联：状态机校验、幂等、已结束/冲突转人工确认。
- 定义岗位删除策略并保护关联申请。
- 增加安全 JSON 全量导出、恢复说明与恢复测试。
- 统一数据库迁移策略，避免运行时 schema 漂移。

**验收标准：** 不会因邮件或删除操作静默损坏申请历史；可在隔离新库完整恢复导出数据。

### 第二阶段：让已做功能真正可用（P1/P2）

- 雷达可见的任务筛选和长标题卡片修复。
- 首次引导、全局待办入口、稳定岗位详情页。
- 工作台和进度页突出“下一步”，并完善邮件同步状态/错误反馈。
- 导入全量问题汇总与统一错误页。

**验收标准：** 新用户能从首页完成“收录 → 准备投递 → 确认投递 → 记录下一步”；用户无需构造 URL 即可找到临期、高匹配、收藏和待确认邮件。

### 第三阶段：智能化可信升级（后续独立决策卡）

- 设计 AI 匹配的统一评分卡、证据和用户纠错数据。
- 设计邮件解析的分步可观测性、人工确认与回归样本集。
- 基于真实使用样本和明确成功阈值，比较外部方法/开源方案；不以“更像 AI”为目标替代可解释性与隐私边界。

**验收标准：** 每个 AI/邮件结论可解释、可纠正、可追溯；低置信和冲突结果不会自动改变申请状态。

## 诊断限制与未下结论事项

- 未实际连接用户邮箱、真实 IMAP 服务或外部 AI 服务，避免访问凭据、邮箱内容与产生外部调用；相应网络、权限、限流和供应商输出稳定性需另行做授权后的集成测试。
- 浏览器自动化环境不能访问本机隔离端口，因此未将其作为视觉结论依据；页面视觉审查基于用户提供的运行截图、模板和 CSS，页面/接口行为基于源代码与 48 项自动化测试。
- 未进行第三方竞品、商业软件或开源项目研究；因此本报告只评价当前实现，不宣称外部方案一定更好。
- 未把“没有独立公司管理”或“未实现云同步/提醒”等现有范围外能力视作代码缺陷；它们仅在用户明确需要时进入下一轮决策。
