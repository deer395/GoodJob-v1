## 1. 摘要

CampusAI 是面向中国校招生的个人秋招助手，帮助用户在截止日期前完成真正适合自己的有效投递，并持续了解每份申请的下一步行动。它不是自动海投工具，也不把邮件待办当作完整求职流程。

V1 采用“先手动闭环、后智能化”的路线：先让用户能可靠收录、评估和管理岗位，再逐步增加匹配、邮件、日历与提醒。

## 3. 背景

现有邮件助手可以把笔试、面试等邮件转为待办，但只覆盖投递后。校招生的实际困难还包括：从分散信息中发现岗位、判断是否值得投、准备材料、按时提交，以及在多个申请并行时不遗漏下一步。

因此产品从“邮件 → 待办”演进为“岗位 → 申请 → 事件”，覆盖投递前、投递中和投递后完整旅程。

## 4. 目标与指标

### 北极星指标

**高匹配岗位在投递 DDL 前完成有效投递的比例。**

有效投递必须满足：用户在官方渠道自行提交；系统保存公司、岗位和投递时间；存在明确后续状态或下一步行动。

### 辅助指标

- 关键 DDL、笔试、面试的遗漏率；
- 从发现岗位到完成投递的耗时；
- 推荐和邮件关联被人工纠错的比例；
- 闭环 1：用户能否在 30 秒内完成一条岗位收录。

当前指标均是待建立基线的产品假设，不把目标值当作已验证结果。

## 5. 目标用户与价值主张

目标用户是同时从官网、公众号、招聘软件、共享秋招表和邮件处理求职信息的中国校招生。

| 用户任务 | CampusAI 提供的价值 |
|---|---|
| 发现岗位后快速留下可行动记录 | 不再把岗位散落在聊天、收藏夹和浏览器标签页中 |
| 判断岗位是否值得投入 | 用截止日期、个人约束和可解释信息辅助决策 |
| 完成投递并持续跟进 | 将岗位、申请、邮件和下一步行动组织为一个流程 |

## 6. 已确认方案与边界

### 用户旅程

```text
投递前：发现岗位 → 收录 → 评估 → 排定优先级
投递中：准备材料 → 核对资格/DDL → 打开官方入口 → 用户手动提交
投递后：追踪申请 → 处理测评/笔试/面试/Offer → 提醒与更新
```

### 严格边界

- 不自动登录、填写或提交任何招聘平台；最终提交权属于用户。
- 不未经授权抓取受限招聘平台或付费文档。
- 不在云端保存 IMAP 授权码、完整邮件正文、完整简历或截图原件。
- 低置信自动化结果必须进入人工确认，不能静默改变申请状态。
- 不生成不存在的经历、技能或简历内容。

### 技术路线

```text
FastAPI + Jinja2 + 少量原生 JavaScript + HTMX（渐进增强）+ SQLite
```

首版为本地个人单机使用。未来若需要跨设备同步，云端使用 PostgreSQL 与登录认证；邮件授权码仍只留在本机 Agent。

## 7. 分阶段方案

| 阶段 | 目标 | 已确认范围 |
|---|---|---|
| 闭环 1 | 30 秒手动收录岗位 | 公司、岗位、城市必填；候选重复处理；DDL 状态；岗位池 |
| 闭环 2 | 秋招雷达 | 搜索筛选、收藏、今日新增、本周截止、个人画像、硬规则排序；CSV/Excel 导入留待 Phase 2 |
| 闭环 3 | 投递工作台 | 收藏/待投递/已投递、检查清单、官方入口、手动投递确认、下一步行动 |
| 闭环 4 | 申请进度 | Application 阶段、事件时间线、漏斗、下一步行动计划时间与本地日历视图；邮件、外部日历同步与提醒后置 |
| Phase 2 | 智能输入与可解释 AI | 已交付本地 CSV/XLSX 导入、用户主动 JD 文本提取、单岗位 AI 辅助判断、本地 IMAP Agent 与邮件待确认流程；OCR 与简历优化仍未实现。 |
| Phase 3A | 岗位匹配架构验证 | 无 JD 岗位池采用本地确定性规则 + n-gram baseline 主排序。LLM 不影响主 `match_score`；结构化调用能力保留给后续经验证的主动单岗位/完整 JD 深度分析。不引入 embedding、向量数据库或 reranker。 |

闭环 4 详见 [闭环 4 决策卡](decisions/loop-4-application-progress.md)。Phase 2 第一批详见 [导入与日历导出决策卡](decisions/phase-2-first-batch-import-calendar.md)：本地文件解析和用户下载 ICS 均不接入外部同步、提醒或自动化状态更新。

## 8. 假设、风险与验证

| 类型 | 当前假设 | 验证方式 |
|---|---|---|
| 价值 | 用户会优先使用“手动收录”而非继续依赖收藏夹 | 用真实岗位连续收录并复盘遗漏情况 |
| 可用性 | 三个必填字段足以让用户开始管理岗位 | 测试 5 条连续录入与缺失字段反馈 |
| 数据 | 同公司/岗位/城市不一定是重复记录 | 以部门/业务线和用户确认处理候选重复 |
| 隐私 | 邮件和截图自动化需要显式同意 | 在 Phase 2 前验证用户接受度与数据最小化方案 |

### Phase 3A：岗位池初筛与 AI 深度分析的分工

- **岗位池初筛：** 目的为在大量稀疏岗位信息中提供稳定、快速、低成本的优先级排序；机制为本地 baseline，不是适配概率或第二套 AI 百分比。
- **AI 深度分析：** 当前页面保留用户主动触发的既有单岗位 AI 辅助分析，输出 `ai_score + reasons + risks`，不反向修改岗位池主排序。完整 JD 的 structured LLM 能力/证据映射是已保留的后续边界，尚未作为当前交付宣称完成。
- 两者是“快速筛选 → 深入判断”的协作，不是两套竞争的匹配分数。AI 能否进入主决策链路必须先经独立人工 Eval 证明。

## Phase 2 第三批补充：本地 IMAP 邮件待确认

用户可在“申请进度 → 邮件待确认”主动点击一次“同步邮箱”。该操作只运行本机、只读的 IMAP Agent，读取后仅保留标题、发件域名和最多 200 字脱敏摘要；不会常驻监听，也不会自动创建岗位、申请或改变申请阶段。AI 解析不合规时，仅对明确的测评/笔试、面试、Offer、拒信关键词给出低置信本地分类，仍必须由用户确认关联或手动补记。

### 2026-08-09 补充：关键时间语义

申请进度把岗位投递 DDL 与投递后事件严格分离：岗位 DDL 仅保留在岗位记录；事件分别保存通知／发生日期、已确认的安排时间与已确认的行动截止。邮件解析仅提出候选安排或行动截止，用户分别确认后才写入事件。表格视图除岗位 DDL 外，另显示下一关键节点，不以历史投递 DDL 代替后续行动。

- 秋招雷达提供临期、今日新增、本周截止、收藏、高匹配和待评估的可见快捷筛选；筛选与搜索词同时生效，并展示当前条件、结果数和一键清除。

- 本阶段不修改 AI 匹配、邮件解析策略或邮件关联状态机；上述能力升级仍需后续独立决策。

## 当前交付更新｜Phase 2 第四批第一阶段（2026-08-09）

本地个人版已补充以下数据安全能力：

- 高置信邮件仅在唯一精确匹配且申请状态机允许时自动关联；同一邮件不会重复创建申请事件，冲突和已结束申请均转人工确认。
- 岗位一旦存在任一申请记录即不可删除，以保护申请、事件与检查项历史。
- 提供脱敏 JSON 全量导出，以及“隔离验证 → 备份当前库 → 全量替换 → 重开数据库健康检查”的恢复路径；第一版不支持合并恢复。
- 启动时由 Alembic 显式迁移并验证 SQLite schema，减少运行期 schema 漂移。

本阶段不改变最终投递权，不保存邮箱授权码、邮件全文或外部 API Key；不包含雷达界面优化、AI 匹配重构或邮件解析算法升级。
## 当前交付修订｜数据安全验收边界（2026-08-09）

- 删除岗位必须有服务端确认；有任一申请的岗位不可删除，反馈会显示关联申请数量。
- 本地 JSON 导出采用字段白名单和邮箱脱敏，不含 `message_id`、凭据或邮件全文，并携带应用版本。
- 恢复完成替换后处于“等待重启健康检查”状态；Web 不会提前报告成功。重新启动并通过迁移、schema 和外键检查后才算恢复成功。
- 非 head SQLite 数据库在 Alembic 升级前自动备份；不可逆迁移依赖备份恢复。
## 当前交付修订｜数据管理与安全删除入口（2026-08-09）

- 所有主页面导航均可进入“数据管理”，用户可自然发现全量导出与恢复。
- 岗位详情提供受确认保护的删除入口：显示关联申请数；有申请即拒绝，无申请且服务端确认后才删除。
- 无 JavaScript 时仍可通过服务端确认页完成或获知拒绝原因。
