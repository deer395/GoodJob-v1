# 决策卡：闭环 4｜申请进度

状态：已确认，实施中。版本：v3（2026-08-06）。

## 用户目标

用户需要回答“我投了哪些、分别走到哪一步、下一步该做什么”，并通过漏斗了解申请转化；最终投递和状态判断始终由用户手动完成。

## 数据与状态

- `Application` 独立承载申请状态，不改变 `JobPosting` 的待评估与收藏语义。
- 状态：待投递、已投递、测评/笔试、面试、Offer、已结束。
- 正常推进为已投递→测评/笔试→面试→Offer；允许跳阶段和同阶段追加事件；已结束可从任一投递后阶段进入；推进操作不允许回退。
- 只有当前为已投递时可沿用闭环 3 撤回到待投递；撤回保留全部既有事件与投递资料。
- `next_action_due_at` 只记录和展示计划时间，不产生提醒。

## 事件与历史数据

- 每次推进必须创建 `ApplicationEvent`；添加事件只记录时间线，不改变状态。
- 时间线以最近事件优先展示：默认最多 3 条，按事件日期、创建时间降序；可展开完整时间线。空描述生成可读默认描述。
- 确认投递时创建“已投递”事件。迁移一次性为已有 `applied_at` 且缺少该事件的记录补建，绝不伪造后续阶段事件。

## 页面与反馈

- 新增“申请进度”入口：列表与日历是同级子视图。顶部列表视图含按曾到达阶段计算的漏斗、阶段筛选和申请卡；日历仅投影已有事件、岗位 DDL 与下一步计划时间。
- 待投递不进入本页；已结束默认折叠。活跃卡展示状态、投递时间、来源、历史 DDL、下一步行动与计划时间、可展开时间线。
- 推进、添加事件与下一步行动编辑均提供普通表单路径；HTMX 仅作局部刷新增强。
- 成功反馈示例：`已更新：公司 · 岗位 → 面试`。

## 异常与边界

- 非法状态、无效事件类型、回退推进与不存在的申请均拒绝并给出可读反馈。
- Offer 不把原岗位 DDL 作为风险提示；DDL 仅作历史信息。
- 不实现邮件解析、IMAP、ICS 导出、外部日历同步、提醒、AI、OCR、爬虫、自动投递、导入或独立面试轮次实体。

## v2 变更记录

用户验收确认需要先看到最新动态，而非从最早事件开始浏览。因此时间线由 v1 的正序调整为倒序，并增加事件数量、友好时间格式和完整时间线展开入口；不影响事件存储、漏斗口径或状态流转验收。

## v3 变更记录

用户确认日历是闭环 4 的本地数据视图，而非外部同步能力。新增列表/日历子视图：绿色为岗位 DDL、蓝色为面试、黄色为测评/笔试、灰色为投递、红色为下一步计划；日格显示数量并可展开当天事项。没有新增表、外部 API、ICS 文件或提醒能力。

## 验收

- 合法状态推进、跳阶段、结束、同阶段事件、撤回兼容、历史投递事件补建和漏斗口径均有自动化覆盖。
- 下一步行动及计划时间刷新后保持；待投递不出现在申请进度页；既有三条闭环测试回归通过。
